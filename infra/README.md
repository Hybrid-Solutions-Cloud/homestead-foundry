# infra/

Parameterized Bicep that deploys a whole Azure AI Foundry environment at
subscription scope. This is what the [deployment guide](../docs/guide/deployment.md)
runs; read that first if you want to deploy. This file explains the layout.

## Layout

| File | What it does |
|---|---|
| `main.bicep` | Subscription-scope entry point. Composes every CAF resource name from its parameter segments and calls the modules in dependency order. |
| `types.bicep` | Shared user-defined types: the model registry entry shape, and the deploy-time model catalog map. Mirrors `models/registry.schema.json`. |
| `modules/resource-group.bicep` | The single resource group everything lives in. Deleting it is the entire teardown. |
| `modules/foundry-account.bicep` | The AIServices account, its registry-driven model deployments, and the optional project. |
| `modules/rbac.bicep` | The two least-privilege data-plane role assignments, granted to security groups rather than individuals. |
| `modules/keyvault-secret-refs.bicep` | Records the secret-name contract only. Never creates a vault, never reads or writes a secret value. |
| `modules/budget.bicep` | The resource-group-scoped monthly budget and its alert thresholds. |
| `params/example.bicepparam` | Minimal shape reference with placeholder values. Not deployable as written. |
| `params/starter.bicepparam` | The one to copy. Wired to the real starter registry, with deployer values marked `REPLACE`. |

## Three design rules worth knowing before you edit

**One region, threaded from one parameter.** Every module that takes a location
takes it from `main.bicep`'s single `location` parameter. Nothing derives its own
region. This is what makes a full teardown and redeploy land cleanly in one place
instead of leaving resources scattered across regions.

**The registry decides what gets deployed, not the template.** Model deployments
are generated by looping over registry entries with `status: deployed`. Adding a
model is a registry edit plus a catalog regeneration, never a template change. If
you find yourself adding a hardcoded model resource here, the registry is the
right place instead.

**Capacity is per model, and the template parameter is only a fallback.** Each
registry entry may carry its own `capacity`. `modules/foundry-account.bicep`
resolves it as `m.?capacity ?? capacity`: the entry wins, and `main.bicep`'s
`modelDeploymentCapacity` parameter is used only for an entry that declares none.
That parameter defaults to `1` so a pre-capacity registry file still deploys, and
`1` is not a number anyone should ship: it measures at roughly one request per
minute and breaks an agentic caller on its second call. Capacity units are not
comparable between models, so a single stack-wide value pins the whole account to
the smallest sensible number.

Because omitting `capacity` is silent, `main.bicep` surfaces it as a drift output
alongside the region check:

| Output | Meaning | Want |
|---|---|---|
| `regionMismatchedRegistryIds` | Deployable ids whose declared `region` differs from `location`. Deployments are children of the account and always land in `location`, so a mismatch is a registry error. | empty |
| `inheritedCapacityRegistryIds` | Deployable ids that declared no `capacity` and are therefore deploying at `modelDeploymentCapacity`. | empty |

Neither is fatal. Both are visible in `what-if`, which is where they are meant to
be read. Raising capacity does not itself cost anything on a `GlobalStandard`
deployment: billing is per token consumed, so it raises the rate ceiling rather
than creating spend. Cost control is the budget, its alerts, and a cap in the
caller.

## Names

Every resource name is composed rather than passed in, so the CAF pattern cannot
drift. Bicep has no pattern decorator, so each segment is its own length-constrained
parameter and the names are built from them:

```
rg-<workload>-<env>-<regionToken>-<instance>
aif-<workload>-<env>-<regionToken>-<instance>
proj-<workload>-<purpose>-<instance>
budget-<workload>-<env>-<regionToken>-<instance>
```

`aif` is the current Microsoft Learn abbreviation for a Cognitive Services account
of kind AIServices. `ais` denotes a different kind and is not used here.

## Validating without deploying

```bash
az bicep build --file infra/main.bicep
az deployment sub what-if --location <region> \
  --template-file infra/main.bicep \
  --parameters infra/params/<your>.local.bicepparam
```

Both are read-only. `*.local.bicepparam` is gitignored, which is where real values
belong; nothing in this directory should ever contain a real subscription, tenant,
group object id, vault name, or email address.

## The other two deployment targets

`infra/` gained two sibling subtrees in Phase P, per
[ADR-0017](../docs/adr/ADR-0017-deployment-target-documentation-structure.md)
decision 6. **The cloud stack stays at the root**; nothing above this line moved.

| Subtree | Target | Form | Status |
|---|---|---|---|
| `windows-server/` | Foundry Local | Imperative PowerShell, delivered by Azure Arc run command | **Written, never executed** |
| `azure-local/` | Azure Local Foundry | Three layers: `kubectl` and Helm, then Bicep, then `kubectl` | **Written, never executed** |

Neither is proven. Foundry Local is blocked on an owner-authorized install test
against a disposable build VM, and Azure Local Foundry is blocked on preview
access plus an AKS Arc cluster. Read each subtree's README before running
anything.

Two things worth knowing without opening them:

- **Foundry Local is imperative because it is not an Azure resource.** There is
  nothing for ARM to create. Arc governs the host, and Arc run command executes
  a script. It also **cannot read state, only run an action**, so idempotence is
  a contract those scripts implement rather than a property of the tooling.
- **Azure Local Foundry's `what-if` covers one layer of three.** Bicep owns only
  the platform layer; the Gateway API and Istio prerequisites underneath it and
  the `ModelDeployment` intent above it are `kubectl`. There is no single command
  that shows the state of that deployment.
